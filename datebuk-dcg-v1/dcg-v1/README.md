# DateBuk Communications Gateway v1.0 — Integration Scaffold

**Status: NOT PRODUCTION READY.** This is a security-first reference implementation and integration starter, not a completed DateBuk deployment. No repository integration, provider validation, end-to-end tests, or live messaging was performed.

## Scope
- Tenant-scoped PostgreSQL provider accounts, senders, consents, messages, audit and webhook event tables.
- AES-256-GCM at-rest encryption for provider secrets (replace local env key with KMS-backed envelope encryption for production).
- Twilio REST SDK with API Key SID/secret or Account SID/Auth Token fallback.
- Redis/BullMQ message queue with retry and idempotency foundation.
- Admin account/sender API validation, default-deny authorization placeholder.

## Setup (isolated development only)
1. Node.js 20+, PostgreSQL 16+, Redis 7+ required.
2. `cp .env.example .env` and populate local environment values. Do not commit `.env`.
3. `npm install` then apply `sql/001_init.sql` using `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/001_init.sql`.
4. `npm test` and `npm start`.
5. All administrative and send routes intentionally fail closed until integrated with the actual DateBuk authentication and entitlement services.

5. Add outbox transaction semantics and provider reconciliation: a timeout after Twilio accepts a send can cause duplicates on retry. The current worker must not be enabled for real traffic until that is addressed.

## Twilio identifiers
- `AC...` Account SID: issued by Twilio, not generated by DateBuk.
- Auth Token: secret used for authentication and webhook signature verification; never expose to clients.
- `SK...` API Key SID + secret: preferred for REST API authentication.
- `MG...` Messaging Service SID: issued when a Messaging Service is created in Twilio.
- Sender number: provisioned/authorized E.164 number, e.g. `+1XXXXXXXXXX`.

Use Twilio Console for provisioning. Do not use fabricated SIDs or sender numbers for live delivery.
